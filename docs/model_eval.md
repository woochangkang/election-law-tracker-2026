# 수집 모델 역량 검토 — Sonnet 5.5(운영) vs Opus 5.5(시험)

목적: 일일 수집 루틴의 Sonnet 5.5가 충분한지 Opus 5.5와 같은 조건에서 비교해, 운영 모델을 유지할지 바꿀지 정한다.

## 시험 설계
- **운영 루틴** `2026 election law tracker daily` (Sonnet 5.5, 08:00 KST) → `main`에 push → 사이트 반영
- **시험 루틴** `2026 election law tracker — Opus eval` (Opus 5.5, 같은 08:00 KST) → `eval/opus-<RUN>` 브랜치에만 push. 배포 워크플로는 main만 보므로 사이트에 영향 없음
- 같은 시각·같은 `data/cases.json`·같은 프롬프트(`prompts/legal_daily.md`)로 출발하므로 차이는 모델에서 온다
- 기간: 2026-10-10 ~ 10-12(KST) 3회. 시험 루틴 cron이 이 사흘만 돌도록 날짜를 박아 두었다(`0 23 9,10,11 10 *` UTC)

## 검토 절차 (2026-10-13 이후, Claude Code 세션에서)
1. **산출물 대조**: `git fetch origin && python3 scripts/compare_runs.py 2026-10-10 2026-10-11 2026-10-12 > evals/2026-10-12_model_compare.md`
   - 자기 보고 검색 횟수(공화·민주·주제), 후속 확인 대상 대비 수행, 움직임·확인·새 사건·거부 건수, 상태 변경 제안, court 출처 비율
   - 한쪽만 찾은 움직임과 새 사건 목록
2. **실제 도구 호출 수**: audit 숫자는 자기 보고라 그대로 믿지 않는다. `RemoteTrigger list_runs` → `get_run_log`로 두 루틴의 회차별 WebSearch·WebFetch 호출 수, 소요 시간, 오류(차단·재시도)를 센다
3. **품질 표본 확인**: 한쪽만 찾은 움직임 전부와 공통 움직임 5건을 출처 URL로 직접 열어 (a) 실제로 있는 사실인가 (b) 날짜·법원 결론이 맞는가 (c) 범위(§1) 안인가를 판정한다. 틀린 항목 수를 모델별로 센다
4. **브리핑 비교**: 같은 날 `briefings/RUN.md` 두 편을 나란히 읽고 누락·과장·문체 차이를 메모

## 판정 기준 (제안 — 검토 시 사용자와 확정)
- **Sonnet 유지**: 사흘 합계에서 Opus만 찾은 *검증된* 움직임이 Sonnet 대비 20% 미만으로 많고, Sonnet의 후속 확인 수행이 대상의 90% 이상이며, Sonnet 오류(사실·날짜 틀림)가 Opus보다 많지 않을 때
- **Opus 전환**: Opus만 찾은 검증된 상태 변경(판결·정지·기각)이 1건이라도 있거나, Sonnet의 후속 확인 수행이 대상의 90% 미만이거나, Sonnet 오류가 Opus보다 많을 때
- **혼합 검토**: 차이가 새 사건 발굴에만 있으면 주 1회 Opus 심층 회차를 따로 두는 안
- 비용·소요 시간도 함께 기록한다(실행 로그 기준)

## 정리
- 판정 후 시험 루틴은 비활성화(이미 날짜 제한), `eval/opus-*` 브랜치는 결과를 `evals/`에 남긴 뒤 삭제
- 전환하면 운영 루틴의 model만 바꾼다(프롬프트는 그대로)
